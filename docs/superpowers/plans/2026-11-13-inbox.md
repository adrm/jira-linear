# Inbox Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add an Inbox view that shows one row per changed ticket, filtered by user-configurable rules, with read/unread, archive and delete, and the ticket open in a right-hand pane.

**Architecture:** The server's incremental sync detects events (changelog entries, new comments, new tickets), filters them with the rules, and stores one entry per ticket plus its events in the mirror SQLite database. The web app reads the inbox from a small HTTP API, the same way it already reads review marks, and applies read/archive/delete optimistically. Rules live on the server and are edited from the settings dialog.

**Tech Stack:** Deno + `node:sqlite` (server, tests with `deno test` and `FakeJira`), React + zustand + vitest (web).

**Spec:** `docs/superpowers/specs/2026-11-13-inbox-design.md`

## Global Constraints

- Inbox actions (read, unread, archive, delete) and rule changes never write to Jira.
- Default scope is `"involved"`; involved = assignee, reporter, QA assignee or watcher of the ticket, or the comment mirror holds a comment by the owner or a mention of the owner on it.
- Mentions and assignment to or from the owner are delivered whenever their rule is on, whatever the scope. New tickets depend only on their own rule. Everything else depends on its rule and the scope.
- Default rules: mentions on; assigned on; status `any`; comments `all` (within scope); new tickets `assigned`; priority, due date, title, labels, type, parent, links off.
- Events by the owner never create entries and never change an existing entry's state.
- Event identity is the changelog history id plus item index, the comment id, or the ticket key for creation; re-detecting an event never duplicates it.
- Changelog entries and comments dated at or before the recorded install time never create events. A full sync creates none.
- Comment edits and description edits create no events; description mentions are not scanned.
- Archived entries return to unread on a new matching event; a read entry becomes unread; a deleted entry's ticket creates a fresh entry on its next matching event.
- An entry whose ticket is tombstoned is removed.
- Opening a ticket anywhere marks its entry read.
- Commit messages follow the repository style (`jira-linear: <what changed>`) and carry no attribution lines.
- Run one server test file: `deno test --allow-net --allow-read --allow-write --allow-env --allow-run server/<file>`; all server tests: `deno task test`; web tests: `cd web && npm test`.

## Review Focus

- A mention nested inside an ADF list or quote still counts as a mention of the owner (test in Task 3).
- A second sync over the 2-minute overlap window returns the same events and adds nothing (Task 4).
- Events dated at or before the install time, including on an existing install with a cursor, add nothing (Task 4).
- A changelog history containing both the owner's change and a colleague's change yields only the colleague's event (Task 3).
- A rules payload that is malformed (unknown scope, `status.mode` of `into` with no statuses, non-boolean field flag) is rejected with 400 and leaves the stored rules unchanged (Task 5).

### Task 1: Shared types and rule evaluation

**Files:**
- Create: `shared/inbox.ts`, `server/inbox_rules.ts`
- Test: `server/inbox_rules_test.ts`

**Interfaces:**
- Produces, in `shared/inbox.ts`:
  - `type InboxEventKind = "created" | "status" | "assignee" | "priority" | "duedate" | "summary" | "labels" | "type" | "parent" | "links" | "comment"`
  - `interface InboxEvent { id: string; key: string; kind: InboxEventKind; at: string; author: UserRef | null; from: string | null; to: string | null; excerpt?: string; mentionsMe?: boolean; assignment?: "to-me" | "from-me" }`
  - `type InboxState = "unread" | "read" | "archived"`
  - `interface InboxEntry { key: string; state: InboxState; updatedAt: string; readAt: string | null; events: InboxEvent[] }`
  - `interface InboxRules { scope: "involved" | "project"; mentions: boolean; assigned: boolean; status: { mode: "off" | "any" } | { mode: "into"; statuses: string[] }; comments: "off" | "mentions" | "all"; newTickets: { mode: "off" | "assigned" | "all" | "epics"; epics: string[] }; fields: { priority: boolean; duedate: boolean; summary: boolean; labels: boolean; type: boolean; parent: boolean; links: boolean } }`
  - `const DEFAULT_RULES: InboxRules` with the Global Constraints defaults.
  - `type InboxAction = "read" | "unread" | "archive" | "unarchive" | "delete"`
- Produces, in `server/inbox_rules.ts`:
  - `isInvolved(issue: Issue, meId: string, watched: ReadonlySet<string>, commentKeys: ReadonlySet<string>): boolean` (`commentKeys` holds tickets whose comment mirror has a comment by or mentioning the owner)
  - `shouldNotify(ev: InboxEvent, issue: Issue, rules: InboxRules, involved: boolean): boolean`
  - `validateRules(input: unknown): InboxRules | null` (null when malformed; fills nothing in, rejects missing keys)

### Task 3: Event detection

**Files:**
- Create: `server/inbox_detect.ts`
- Test: `server/inbox_detect_test.ts`

**Interfaces:**
- Consumes: `InboxEvent` (Task 1).
- Produces: `detectEvents(raw: any, known: { commentIds: ReadonlySet<string> }, meId: string, installedAt: string): InboxEvent[]` where `raw` is a Jira issue payload fetched with `expand=changelog` and the `comment` field. Returns events oldest first, with: a `created` event when `raw.fields.created` is after `installedAt`; one event per changelog item whose field maps to a kind (the same mapping as `FIELDS` in `server/activity.ts`, plus `Link` to `links`) and whose history is after `installedAt` and not authored by `meId`; one `comment` event per comment whose id is not in `known.commentIds`, created after `installedAt` and not authored by `meId`, with `excerpt` (first 160 chars of the plain text) and `mentionsMe` (an ADF `mention` node with `attrs.id === meId` anywhere in the body). An `assignee` item sets `assignment` to `"to-me"` when its raw `to` equals `meId` and `"from-me"` when its raw `from` equals `meId`. Event ids: `h:<history id>:<item index>`, `c:<comment id>`, `new:<key>`.

- [ ] **Step 1: Write failing tests** in `server/inbox_detect_test.ts`: a status item yields one event with `from`/`to` names; an item by `meId` yields none while a colleague's item in the same issue yields one (Review Focus); a history dated at or before `installedAt` yields none; `created` is emitted only after `installedAt`; assignee items set `assignment` both ways; a comment by `meId` yields none; a known comment id yields none; a comment whose ADF has a mention of `meId` inside a bullet list item sets `mentionsMe` (Review Focus), and a mention of someone else does not; unmapped fields (for example `Rank`) yield none.

**Interfaces:**

When `meId` is set, `syncOnce` (a) reads `store.inboxInstalledAt()` before ingesting, (b) on an incremental run requests `expand=changelog` for the changed issues, (c) before `replaceComments` overwrites a ticket's comments, collects the known comment ids, runs `detectEvents`, filters with the stored rules, and stores survivors with `addInboxEvents`, (d) refreshes the watched set with the search `project = <P> AND watcher = currentUser()` on every run.
